## What is TorchAO

[TorchAO](https://github.com/pytorch/ao) is PyTorch's official quantization toolkit. It can
apply weight-only INT4/INT8/FP8 quantization to `nn.Linear` layers at runtime, without
pre-converting the model to a separate file format. The quantized weights stay in the
original checkpoint; TorchAO replaces the linear layers with quantized equivalents and
runs dequantization on the fly during inference.

This is different from the formats InvokeAI already supports:

| Format | File | Quantization point |
| ------ | ---- | ------------------ |
| GGUF | Pre-quantized `.gguf` | Separate file, loaded as compressed tensors |
| SDNQ | Pre-quantized shards | Separate file, loaded as compressed tensors |
| BnB NF4/INT8 | Pre-quantized file | Handled by `transformers` natively |
| FP8 Storage | Full-precision checkpoint | Post-load hook casts weights to FP8 storage |
| **TorchAO (WIP)** | Full-precision checkpoint | Post-load hook replaces `nn.Linear` with quantized equivalents |

## Why it matters

TorchAO's weight-only INT4 can cut a transformer's VRAM footprint by ~4x with no external
tooling and no separate download. It works on any CUDA device (compute still runs in BF16
unless the hardware has native INT4 tensor cores, in which case there is also a speed win).

The appeal for InvokeAI is that users could point the Model Manager at a normal BF16
diffusers pipeline and toggle INT4 quantization on — no separate GGUF file, no SDNQ
pipeline, no BnB install.

### Blocked / Remaining work

1. **Cache coherence.** The model cache keys by source + hash. TorchAO-quantized weights produce a different runtime module than the full-precision source, but the state dict keys diverge after quantization. The cache must key on quantization config (`format + quant_type + group_size`), not just the checkpoint hash.

2. **State-dict round-trip.** A TorchAO-quantized model cannot be saved through InvokeAI's normal checkpoint pipeline because `state_dict()` returns quantized tensor wrappers, not plain `torch.Tensor`. If the cache evicts and reloads, it must re-quantize from the original full-precision source — which means the original must be retained.

3. **Per-architecture tuning.** The current loader reuses the existing single-file checkpoint loader for each architecture and applies TorchAO on top. This works as a proof of concept but needs per-architecture validation: which layers to skip (norm, embed, proj_out), what group sizes are stable, and whether INT8 is a better default for some models.

4. **Kernel support.** Added `_check_quantization_kernel_support()` to `model_loaders/torchao.py`. INT4 requires CUDA compute capability >= 7.0; FP8 requires >= 8.9; CPU/MPS are rejected for INT4/FP8 with a clear error. Remaining decision: should InvokeAI fall back to INT8 on unsupported hardware, or reject the install outright?

## Planned design

### Scope for v1

- **Runtime-only quantization on load.** The quantized model lives in the in-memory cache
  only. It is never serialized. If the cache evicts, the model is re-quantized from the
  original full-precision source on the next load.
- **INT4 weight-only, per-group.** This is the most impactful setting: ~4x VRAM reduction,
  acceptable quality loss for most prompts, works on any CUDA device.
- **One architecture first.** FLUX.1 is the best target: single transformer, well-understood
  linear-layer layout, active community interest. FLUX.2 Klein and Qwen Image 2.1 follow.

### Config surface

The configs are already implemented in `configs/main.py`:

```python
class Main_TorchAO_Flux_Config(Checkpoint_Config_Base, Main_Config_Base, Config_Base):
    base: Literal[BaseModelType.Flux] = Field(default=BaseModelType.Flux)
    format: Literal[ModelFormat.TorchAOQuantized] = Field(default=ModelFormat.TorchAOQuantized)
    quant_type: Literal["int4_weight_only", "int8_weight_only", "fp8_weight_only"] = "int4_weight_only"
    group_size: int = 128
    variant: FluxVariantType = Field()
```

Equivalent configs exist for `Flux2` and `QwenImage`.

### Loader flow

```
from_model_on_disk()  →  validate full-precision checkpoint exists, reject already-quantized
        ↓
_load_model()         →  load full-precision weights into model
        ↓
_apply_torchao()      →  ao.quantize_(model, quant_type=..., group_size=...)
        ↓
cache (keyed by source + hash + quant config)
```

### Cache key

The cache key must include the quantization config, not just the checkpoint hash. Two
entries for the same BF16 checkpoint:

```
key = f"{source}:{hash}:torchao:int4:group128"
key = f"{source}:{hash}:torchao:int4:group64"
```

These are distinct cache entries. Evicting one does not affect the other.

## Open questions

- **Granularity.** Per-group INT4 (group_size=128) is the TorchAO default and gives the
  best quality/size trade-off. Should InvokeAI expose group size to users, or fix it per
  architecture?
- **Kernel support.** Added hardware detection in `model_loaders/torchao.py`. INT4 requires
  CUDA compute capability >= 7.0; FP8 requires >= 8.9; CPU/MPS are rejected for INT4/FP8.
  Remaining decision: should InvokeAI fall back to INT8 on unsupported hardware, or reject
  the install outright?
- **Quality testing.** TorchAO INT4 on FLUX-class models is usable but not lossless. The
  team needs a benchmark suite (FID, CLIP score, prompt adherence) before enabling it for
  general use.
- **Interaction with FP8 Storage.** Both hooks install forward pre/post hooks on the same
  `nn.Linear` layers. If both are enabled, TorchAO should win and FP8 Storage should be a
  no-op — this needs an explicit guard in `load_default.py`.
